# واسط SOCKS خودکار برای اپکلود تریال

این سند جایگزین پیشنهاد استفاده از REALITY در راهبرد قبلی است. درخواست کاربر: سه کانفیگ SOCKS روی سه سرور متفاوتِ سایر اکانت‌ها، پورت مجاز اپکلود و جایگزینی خودکار.

## قرارداد اجرا
- انتخاب‌گر `DOB_UPCLOUD_RELAY_PANELS`: خالی/none خاموش؛ UUID پنل تریال برای آزمایش محدود؛ all برای پنل‌های فعلی و آینده. انتخاب‌گر نامعتبر خاموش می‌ماند.
- حداکثر شش نامزد آماده از سرورهای غیرتریال DigitalOcean/Vultr/Linode با عمر کافی؛ سه سرور و سه IP متفاوت برای هر گیرنده. وابستگی‌های فعال تا جایگزینی حفظ می‌شوند. تنوع شرکت/اکانت ترجیح داده می‌شود؛ استقلال پروکسی نهایی ادعا نمی‌شود.
- پورت اول 8080، سپس 80 و 443 فقط در صورت آزاد بودن در موجودی و قالب پنل؛ هیچ ورودی موجودی بازنویسی نمی‌شود. اتصال واقعی شرط پذیرش عملیاتی است.
- ورودی SOCKS اختصاصی در قالب Xray همان پنل مدیریت می‌شود. رمز تصادفی و کلید TLS در مخزن رمزنگاری‌شدهٔ اکانت ذخیره می‌شوند؛ گواهی اختصاصی همان واسط در گیرنده trusted است؛ TLS verification خاموش نمی‌شود.
- SOCKS بومی UDP خاموش است. XUDP روی همان اتصال TLS/TCP مجاز، UDP را منتقل می‌کند؛ Mux برای TCP خاموش است. REALITY برای این ارتباط استفاده نمی‌شود.
- فقط IPهای دقیق گیرنده‌های تریال فعال، با رمز درست و دسته‌های مجاز می‌توانند از واسط استفاده کنند. مسیر خارج از دسته، منبع ناشناخته و نبود مسیر سالم مسدود می‌شوند؛ fallback مستقیم وجود ندارد.
- اتصال Sanaei و مدیریت سرورها از مسیر مستقیم IPv4 موجود ادامه می‌یابد. سیاست پروکسی مدیریت اکانت‌ها تغییر نمی‌کند.

## سلامت و جایگزینی
هستهٔ گیرنده هر 10 ثانیه با timeout سه‌ثانیه سلامت مسیر را از داخل واسط می‌سنجد. مقصد بررسی BrowserLeaks است؛ پاسخ HTTP پس از TLS معیار اتصال است، نه تضمین پاسخ 200 یا موفقیت همهٔ برنامه‌ها. سرویس هر پنج ثانیه مشاهدات خود هسته را از API مستقیم پنل می‌خواند؛ probe تکراری رزیدنتال ارسال نمی‌کند.

پس از حدود 30 ثانیه مشاهدهٔ مداوم خرابی، واسط برای دو دقیقه کنار گذاشته می‌شود و در چرخهٔ بعدی reconciliation جایگزین می‌شود. هسته قبل از آن بین گزینه‌های موجود جابه‌جا می‌شود. زمان‌ها حدود زمان‌بندی‌اند؛ اتصال‌های باز تضمین انتقال بدون قطع ندارند. نمونهٔ قدیمی یا گم‌شده سلامت محسوب نمی‌شود و انتشار لینک به سلامت تازهٔ مسیر وابسته است. یک مسیر باقی‌مانده می‌تواند سرویس را ادامه دهد، اما پذیرش کامل سه مسیر سالم می‌خواهد.

## انتشار و بازگشت
Migration 167 افزایشی است. ابتدا قابلیت با انتخاب‌گر خاموش نصب می‌شود؛ سپس یک پنل تریال، اثبات واقعی و بازگشت انتخاب‌گر، بعد گسترش. دسته‌های جدید با انتخاب‌گر مستقل قبلی فعال می‌شوند و نیازمند native proof هستند. خاموش‌کردن انتخاب‌گر با همین نسخه، ورودی‌ها و مسیرهای مدیریت‌شده را حذف می‌کند. قبل از بازگشت به باینری قدیمی این پاک‌سازی باید تأیید شود.

آزمون‌های سورس: انتخاب و جایگزینی سه سرور، Postgres ایزوله، ساخت مجدد بدون چرخش بی‌دلیل رمز، پورت اشغال‌شده، گواهی و رمز اشتباه، IP غیرمجاز، TCP/UDP چندمرحله‌ای با Xray 26.9.9 و قطع کامل مسیر. نتیجهٔ عملیاتی در گزارش انتشار جدا ثبت می‌شود؛ این سند به‌تنهایی اعلام پروداکشن نیست.

مصرف OpenAI API در پیاده‌سازی و تست این تغییر تا ثبت این سند: صفر فراخوانی و صفر توکن پروژه. پایش و جایگزینی در محصول به OpenAI API نیاز ندارد.
