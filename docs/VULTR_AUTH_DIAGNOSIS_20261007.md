## یافته‌ها و حدود نتیجه

- پنج کلید متفاوت، غیرخالی و قابل رمزگشایی هستند؛ فاصلهٔ داخلی یا پیشوند Bearer تکراری ندارند.
- درخواست‌ها از runtime فعلی با کنترل مسیر حساب، پروکسی SOCKS5 اختصاصی و TLS معتبر عبور کردند؛ مسیر مستقیم جایگزین استفاده نشد.
- TOKEN_INVALID نام دسته‌بندی فعلی ربات برای 401 است. این نام به‌تنهایی اثبات نمی‌کند کلید توسط کاربر لغو شده است.
- دادهٔ فعلی دلیلی برای نسبت‌دادن خطا به بدهی، سقف سرور یا محدودیت نرخ درخواست ندارد.
- لغو/تعویض کلید، غیرفعال شدن API، محدودیت حساب یا IP و اشکال سمت احراز هویت Vultr از پاسخ عمومی Unauthorized قابل تفکیک نیستند.
- مستندات Vultr می‌گوید کلیدها خودکار منقضی نمی‌شوند و Access Control می‌تواند استفاده از کلید را به IPهای مجاز محدود کند.
- API و هر دو worker فعال‌اند و NRestarts=0 دارند. هیچ استقرار یا ریست حساب/گیت انجام نشد. ایجاد runtime فقط از bookkeeping معمول پذیرش و مشاهدهٔ شبکه استفاده کرد.

## اقدام اصلاحی

۱. در Account → API یکی از حساب‌های خطادار، فعال بودن API، تطابق کلید فعلی با کلید ثبت‌شده، Access Control و پیام‌ها/لاگ دسترسی حساب بررسی شود. کلید کامل در گفتگو یا گزارش منتشر نشود.
۲. بر اساس نتیجه، تنها کلید همان حساب از مسیر ویرایش معتبر ربات به‌روز شود، یا دسترسی موردنظر در کنسول Vultr بازیابی شود. اگر allowlist علت بود، فقط IP خروجی ثابت و موردنظر همان حساب مجاز شود.
۳. موفقیت GET account و instances با پاسخ 200 تأیید شود؛ سپس مشاهده‌گر معمول ربات، با فاصلهٔ بررسی پنج‌دقیقه‌ای، وضعیت را بازیابی کند. کارهای معوق با رعایت همان گیت‌ها و جلوگیری از اجرای تکراری بررسی شوند.
