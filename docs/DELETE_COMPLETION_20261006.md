# Provider-confirmed deletion completion — 2026-10-06

## Incident and source defect
Vultr232 had one local DELETING resource whose matching DELETE_DROPLET operation had been succeeded for more than2 hours. Provider inventory occupancy was14 while local occupancy stayed15;14 additional expired READY resources waited behind that first per-account lifecycle item. Successful operation recovery was committed separately from ConfirmDeleted, and the latter handled DELETING but not the earlier RETIRING state. A local failure or confirmation racing the RETIRING -> DELETING transition could leave an unrecoverable completion gap. The exact historical interleaving is not proven.

## Change
Provider absence confirmation now atomically updates the version-fenced operation, local resource/deployment states and backfill signal in one PostgreSQL transaction. Confirmation accepts already-admitted RETIRING and DELETING, with row locks and active-state rejection. The old transition CAS cannot resurrect a completed deletion. Historical matching succeeded lifecycle-delete receipts are replayed locally before runtime construction; unknown, failed, unrelated and active READY cases cannot be promoted. Duplicate completion does not repeatedly wake the scheduler. All real network calls retain existing proxy/identity/provider gates. No new paid test resources, control reset, operation reset or x-ui setting change.

Retain additive durable evidence on rollback; do not restore an old production database. Backup and rollout evidence: /root/backups/dob-delete-completion-20261006.

Network scope: every production account currently uses proxy_required. Its existing per-request transport checks readiness, sticky identity, generation and epoch, including GET. Explicit legacy RouteDirect has no proxy generation by design and is unchanged; this patch does not introduce a universal direct-route identity gate. Generic owned-resource completion is allowed only without a droplet; a matching droplet requires its exact lifecycle-delete key. Local succeeded receipts remain discoverable under LOCKED/BILLING_BLOCKED, while every unconfirmed provider deletion stays excluded.
