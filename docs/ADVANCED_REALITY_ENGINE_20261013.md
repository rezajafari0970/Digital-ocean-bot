## آخرین ادامه: نمونه شبکه‌ای روی سرور جایگزین

دسترسی به Canary با انتخاب سرور Vultr به آدرس 66.245.221.209 رفع شد. آزمایش مستقل در دو مسیر REALITY/TCP Vision و REALITY/XHTTP با Core رسمی 26.10.10 و سپس کپی Core واقعی 26.9.9 انجام شد؛ کلاینت Linux نسخه 26.5.9 بود. از ۱۵۶ درخواست، ۴۰ مورد لغو عمدی بودند؛ خطای غیرمنتظره ثبت نشد. رد احراز هویت، Rollback کانفیگ نمونه، بازیابی فرایند مستقل و حذف منابع آزمایش تأیید شدند.

تغییر بافر 64→128 بهبود پایدار نشان نداد و به Production راه نیافت. آزمایش گوشی، soak طولانی، Reboot اختصاصی و اعمال/بازگشت زنده پنل همچنان باقی‌اند. کانفیگ اصلی هم‌زمان با jobهای عادی ساخت کاربر تغییر کرد؛ وضعیت جدید حفظ شد. نتیجه و حدود دقیق در `ADVANCED_REALITY_NETWORK_CANARY_20261013.md` و رسید JSON هم‌نام آمده‌اند. اطلاعات Canary مسدود در بخش‌های قدیمی زیر، تاریخچه میزبان قبلی است و وضعیت میزبان جایگزین را توصیف نمی‌کند.

## حدود غیرقابل تغییر

- هیچ APK، کتابخانه Android، Core کلاینت یا پروتکل اختصاصی ساخته نمی‌شود.
- قرارداد JSON: نام کلیدها، نوع داده، ساختار تو‌در‌تو و تعداد/ترتیب عناصر آرایه ثابت می‌ماند. فیلد ناشناخته و همه مقادیر به‌صورت پیش‌فرض غیرقابل تغییرند.
- در نسخه حاضر فقط پیشنهاد تغییر مقدار **فیلد موجود** `policy.levels.<level>.bufferSize` در بازه آزمایشی ۱۶ تا ۵۱۲ KiB و `handshake` در بازه ۴ تا ۳۰ ثانیه پذیرفته می‌شود. این محدوده توصیه به تغییر همه سرورها نیست. `can_apply` همواره false است.
- تغییر UUID، کلید، SNI، مسیر، Host، قواعد خروجی، تعداد Inbound/Outbound، الگوریتم رمزنگاری و مقادیر TLS با این API مجاز نیست.
- bufferSize سقف کل حافظه اتصال/Inbound نیست؛ handshake در policy نیز تمام مهلت‌های TLS، REALITY و HTTP را کنترل نمی‌کند.
- خاموش کردن مشاهده هیچ تغییری در ترافیک ایجاد نمی‌کند. هیچ Worker یا actuator برای اعمال سیاست اضافه نشده است.
- تغییر خودکار، تصادفی یا زمان‌بندی قطع اتصال فعال وجود ندارد. «نامرئی بودن کامل VPN»، «رفع همه DPIها» و «قطع نشدن قطعی» قابل تضمین نیستند.

## یافته مهم آزمایش Native

اجرای اولیه ماتریس نسخه‌ها FAIL شد. تشخیص کنترل‌شده نشان داد Freedom در نسخه جدید مقصد خصوصی Loopback آزمایش را به‌طور پیش‌فرض مسدود می‌کند؛ درخواست به مقصد synthetic نرسیده بود. این خطا شاهد خرابی XHTTP نبود.

Baseline مستقل آزمایش با یک `finalRules` استاندارد و محدود به `127.0.0.1/32`، TCP و **پورت تصادفی همان مقصد تست** ساخته شد. این استثنا در محیط آزمایش است و در تولید کانفیگ، validator تغییرات یا هیچ سرور Production اعمال نمی‌شود. پس از اصلاح fixture هر سه جفت نسخه PASS شدند؛ رسیدهای FAIL اولیه نیز حذف نشده‌اند.

هر مسیر مثبت ۷۲۰٬۸۹۶ بایت داده مصنوعی را با کنترل SHA-256 عبور داد. تغییر آزمایشی فقط buffer موجود از ۶۴ به ۱۲۸ بود؛ مسیر بازگشت از Snapshot واقعی خوانده شد. گواهی TLS مقصد آزمایش به‌طور صریح مورد اعتماد همان تست بود؛ `allowInsecure` فعال نشد. REALITY با کلید و Short ID مصنوعی اجرا شد. نام گواهی غلط و Short ID غلط نتوانستند همان جریان را برقرار کنند.

این آزمون‌ها پایداری طولانی، توان عملیاتی WAN، ظرفیت HTTP/2، شبکه موبایل، نسخه Android یا مقاومت در برابر DPI را اثبات نمی‌کنند.

| Firewall / Conntrack | شمارش/سنجش، فقط قانون متعلق به آزمایش | بله، پس از بررسی مالکیت | SSH و پورت‌های موجود حفظ؛ حذف فقط rule/chain متعلق به آزمایش |
| خروجی / SNI | scorer موجود، health مقصد، حفظ routing و residential ownership | scorer موجود؛ مهاجرت جداگانه | کانفیگ منتشرشده ثابت؛ fail-closed recovery دست‌نخورده |

تغییر الگوریتم رمزنگاری یا handshake اختصاصی در این برنامه وجود ندارد. زمان‌بندی خروجی استاندارد و کنترل ازدحام ممکن است رفتار را بهتر کند؛ سرور نمی‌تواند ClientHello، ترافیک قبل از رسیدن به سرور، اعتبار IP یا همه ویژگی‌های آماری دو سمت را کنترل کند.

## سنجش و تصمیم هوشمند

| سنجه | منبع قابل قبول | وضعیت اولیه / محدودیت |
|---|---|---|
| فهرست Inbound، protocol، port، transport، امنیت، client count | snapshot native موجود در DB | پیاده‌سازی خواندن؛ timestamp و freshness مستقل |
| سلامت routing | `panel_routing_state` | مشاهده موجود؛ شاهد اتصال واقعی از ISP کاربر نیست |
| CPU/RAM/interface throughput/FD | guardian موجود یا host census | داده تازه ناموجود به null/Unknown تبدیل می‌شود؛ throughput رابط، goodput تونل نیست |
| RTT/P95/jitter/reset/retransmission | probe کنترل‌شده + TCP_INFO/counters با scope مشخص | در جمع‌آورنده فعلی اندازه‌گیری نشده؛ host counter به یک کاربر نسبت داده نشود |
| TLS/REALITY/XHTTP موفق/ناموفق | شمارنده در مرز واقعی هر مرحله | نیازمند instrumentation؛ نبود خطا در log معادل صفر خطا نیست |
| Stream، buffer، queue، GC، handshake budget | instrumentation Core و metrics runtime | فعلاً BLOCKED؛ شمارش اتصال برابر Stream نیست |
| DNS/IP/TCP/TLS/REALITY/XHTTP failure | آزمایش مرحله‌ای از دو نقطه و confidence | Timeout تنها علت را قطعی نمی‌کند |
| ادعای DPI | مقایسه کنترل‌شده از شبکه‌های هدف، شاهد تکرارشونده و کنترل خارج شبکه | هیچ تضمین یا نتیجه قطعی در این مرحله وجود ندارد |

ابزار `advanced-reality-host-observe.py` فقط aggregate میزبان، sysctlهای خواندنی، kernel/OS، فشار منابع و وضعیت systemd را می‌خواند. اتصال کاربران، IP مقصد، payload، کلید یا capture بسته جمع نمی‌کند. نمونه‌های دارای boot متفاوت نباید برای تفاضل counter استفاده شوند. هیچ تنظیم OS با این ابزار نوشته نمی‌شود.

موتور فعلی فقط **پیشنهاد** می‌دهد: حداقل ۱۰۰ نمونه، داده حداکثر ۶۰ ثانیه، رد زمان آینده و تکرار نمونه؛ ۳ پنجره فشار برای پیشنهاد کاهش پذیرش اتصال جدید؛ ۵ پنجره سالم برای پیشنهاد بازگشت؛ cooldown پنج دقیقه. قطع پیوستگی داده، شمارنده hysteresis را پاک می‌کند. افزایش خطا بیش از ۲ واحد درصد یا P95 بیش از ۲۵٪ فقط پیشنهاد Rollback ایجاد می‌کند. آستانه‌ها قرارداد آزمایش‌اند، نه بهینه قطعی برای تمام سرورها.

## ایمنی، Rollback و حذف

1. حالت پیش‌فرض `DISABLED` است. `DOB_ADVANCED_REALITY_OBSERVE=1` فقط مشاهده و dry-run را فعال می‌کند؛ گزینه‌ای برای فعال‌سازی اعمال ناوگان وجود ندارد.
2. APIهای `GET /api/v1/advanced-reality` و `POST /api/v1/advanced-reality/validate` از auth و نقش Admin موجود استفاده می‌کنند. پاسخ validation شامل hash و مسیر فیلد مجاز است؛ هیچ مقدار حساس یا خطای خام Core برگردانده نمی‌شود. ارسال candidate کامل فقط روی TLS واقعی یا Loopback پذیرفته می‌شود؛ header جعل‌پذیر proxy دلیل اعتماد نیست.
3. CLI آزمایش روی پوشه تازه با permission 0700 و فایل 0600 کار می‌کند. init / stage / status / rollback / export / remove دارای CAS و کلید درخواست پایدار است. baseline و current در یک فایل اتمیک با fsync ذخیره می‌شوند؛ بازگشت، بایت‌های اولیه را دقیقاً حفظ می‌کند.
4. این Rollback مربوط به **فضای آزمایش** است، نه سرویس زنده. Rollback زنده هنوز پیاده نشده و نباید در UI به‌صورت موجود نمایش داده شود.
5. حذف فقط بعد از بازگشت baseline، تطبیق hash و نبود فایل ناشناس انجام می‌شود؛ حذف بازگشتی، بازنویسی تغییرات دیگران یا حذف داده مشترک وجود ندارد. فایل pending ناشی از crash، حذف خودکار را مسدود می‌کند تا بررسی شود.
6. نسخه حاضر migration پایگاه داده، Worker، unit، rule فایروال، sysctl، کلید سرور و تنظیم Inbound جدیدی در Production ایجاد نکرده است. حذف کامل کد از انتشار آینده با revert کردن Commit ویژگی انجام می‌شود؛ پوشه آزمایش متعلق به آن جدا حذف می‌شود. حذف فایل به معنی secure erase رسانه یا حذف نسخه‌های Git/backup نیست.
7. اعمال زنده آینده باید با hash قبل/بعد، generation، قفل مشترک موجود، snapshot رمز/مجوز مناسب، نتیجه نامعلوم پس از crash، verify سلامت و rollback بدون overwrite تغییر خارجی ساخته شود. خاموش‌کردن feature flag نباید obligations حل‌نشده را دور بریزد.

## ترتیب ادامه

1. فراهم شدن میزبان مستقل و خواندن وضعیت پورت ۸۰، سرویس‌ها، منابع، فایروال و backup آن؛ هیچ سرویس موجود برای آزاد کردن پورت متوقف نشود.
2. ثبت hash/version واقعی Core هر پنل و گوشی از مسیر موجود؛ به نسخه مرجع یا عنوان UI اکتفا نشود.
3. اتصال رسمی v2rayNG با schema موجود، TUN/DNS/UDP و تست طولانی؛ نگهداری baseline همراه همان کلاینت.
4. baseline سپس یک متغیر در یک Canary، داده حداقل ۳۰ دقیقه و سپس soak طولانی‌تر؛ معیار پذیرش از baseline همان شبکه محاسبه شود.
5. load/slow reader/cancel/HTTP2/backpressure، memory plateau، OOM ایزوله، crash و reboot روی میزبان اختصاصی؛ PASS واقعی برای Rollback و حذف.
6. اگر کنترل موجود کافی نبود، کوچک‌ترین patch سمت سرور با invariantهای صریح روی فورک جدا؛ Core کلاینت دست‌نخورده.
7. مشاهده shadow سپس Canary یک سرور، چند سرور و درصد کوچک ناوگان؛ توقف گسترش هنگام regression، coverage ناقص، drift یا شکست بازگشت. سراسری فقط پس از گذر این گیت‌ها.

تا قبل از این مراحل، هیچ مقدار buffer/timeout، kernel، SNI، رمزنگاری یا تنظیم ترافیک روی ناوگان عوض نمی‌شود. تست‌های انجام‌نشده PASS نامیده نمی‌شوند.
